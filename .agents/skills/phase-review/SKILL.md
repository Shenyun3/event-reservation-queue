# Phase 门禁代码审查（Rapid Prototype）

本 Skill 用于在每个 Phase 完成并合并子 Worktree 后执行独立盲审。支持同一套代码连续做 **2 轮侧重点不同的审查**，避免重复啰嗦，快速清零阻塞问题。

## 审查原则与权限边界

- **严格只读**：默认只读取代码、文档、日志并运行非破坏性检查命令（`typecheck`、`build`、`lint`、`test`）；**禁止修改源码、格式化文件、提交 Git，也禁止修改 `docs/plan.md` 的勾选状态**（`plan.md` 统一由主 Orchestrator Agent 在验收通过后更新）。
- **先读 4 个基准锚点**：开始读代码前，先核对目标 Phase 在以下文件中的定义：
  1. `demo/`：最高视觉与页面跳转基准。
  2. `docs/plan.md`：本 Phase 的子任务范围与验收标准。
  3. `docs/architecture.md`：仓库目录结构、技术栈与分层约束（如 `Handler -> Service/Usecase -> Repository`）。
  4. `docs/database.md`：数据模型、约束、状态枚举与 Seed 契约。
- **聚焦本次 Phase 增量**：确认比较基线（Phase 起始提交与当前 `HEAD`、以及未跟踪文件），不把未在本 Phase 承诺的功能当成缺陷，但必须核实“本 Phase 声称已完成项”是否真完整。
- **不轻信口头声明**：任何未亲自执行通过的命令、未查看的日志、未实际运行验证的 UI 渲染，一律在报告末尾列入“未验证事项”。

## 双轮盲审分工（支持连续 2 次独立 Review）

调用时若指定了 `Pass 1` 或 `Pass 2`，按对应侧重执行；未指定时默认覆盖完整检查项，并优先输出 `P0/P1`。

### Pass 1：功能闭环、运行态与阻塞缺陷（聚焦 `P0 / P1`）
1. **Plan 验收与 Demo 对齐**
   - `docs/plan.md` 中本 Phase 涉及的所有子任务是否真正闭环？有没有遗漏页面跳转、核心按钮无响应、或本该接真实后端却仍残留写死 Mock 数据？
   - 前后端路由、请求方法、路径参数、响应字段是否实际打通（非“前端调 `/api/x` 而后端写的是 `/api/y`”）？
2. **运行态与日志门禁**
   - 检查 `.logs/backend.log` 与 `.logs/frontend.log` 末尾日志：是否存在启动报错、未捕获异常、500 错误、Prisma 报错、CORS 拦截或 React Hydration/Runtime Error？
   - 执行本项目的确定性检查命令（如 `typecheck`、`build`、关键测试），核实退出码是否为 `0`。
3. **数据契约、安全与并发底线**
   - `docs/database.md`、`prisma/schema.prisma`、Repository 返回类型与 Zod DTO 三者字段和枚举值是否一致？
   - 必须通过 ORM（如 Prisma）访问数据库，禁止在业务/路由层散落手写裸 SQL（项目明确允许除外）。
   - 多表写操作是否放在事务中？是否存在明显的越权访问（直接信任前端传来的 `userId`/`role`）、未校验输入、敏感字段（密码/Token/内部堆栈）泄露给前端？
   - 对象存储是否通过统一 `Storage` 接口映射本地目录，而非直接把绝对路径或二进制塞进数据库？

### Pass 2：架构边界、状态健壮性与代码可读性（聚焦 `P1 / P2`）
1. **Clean Architecture 分层与防过度封装**
   - 严格按 `docs/architecture.md` 检查依赖方向：
     - 路由/Handler 层是否只做参数校验（Zod）、调用 Service/Usecase、映射响应，有没有偷写 Prisma 查询或核心业务规则？
     - Service/Usecase 层是否依赖 Repository 接口/抽象，不直接耦合 HTTP Request/Response？
     - Repository 层是否只负责持久化，不混入业务流程判断？
   - 检查过度拆分与重复造轮子：有没有只转发参数毫无逻辑的空壳包装层？同一查询是否出现两套互相漂移的实现？
2. **前端工程规范与四态完整性**
   - 组件归属是否清晰：`shadcn/ui` 基础原语放在 `components/ui/`，业务无关通用组件放 `components/`，页面/业务专用组件按 `features/<feature>/` 就近聚合。
   - 每个异步交互与数据页面是否显式处理了 **Loading / Empty / Error / Success** 四种状态（避免白屏、报错静默吞掉、重复提交竞态）？
   - 样式是否统一使用 Tailwind CSS 与设计 Token，有无明显偏离 `demo/` 交互与布局的问题？
3. **AI / 外部调用边界（如项目包含 AI 能力）**
   - 模型输出是否经过 Zod 等结构化校验，禁止把展示文案当权威数据解析。
   - 超时、失败兜底与报错提示是否明确，是否在事务外调用慢速外部模型？
4. **可读性、Google Style 注释与清理**
   - 代码是否按“准备 -> 校验 -> 执行 -> 返回”合理分块，避免几百行函数堆叠或超长单文件。
   - **注释检查**：每个核心/新建文件顶部应有职责说明，所有导出函数、类与 Service 方法应遵循 **Google Style 注释规范**（说明意图、参数、返回值与异常/边界）；不要求为 trivial 的内部一行 helper 硬凑注释。
   - 是否有遗留的 `console.log` 调试残片、临时测试路由、死代码或冲突合并残留？

## 报告输出格式

默认使用中文，按实际影响从高到低输出：

1. **审查结论摘要**：一句话给出当前 Phase 是否建议放行进入下一 Phase（`建议放行` / `修复阻塞项后放行`）。
2. **问题清单（按 `[P0]` - `[P3]` 分级）**：
   - **`[P0]` 阻塞上线/演示**：应用跑不起来、核心主流程断裂、数据损坏、严重安全漏洞。
   - **`[P1]` 必须本 Phase 修复**：契约不一致、越层直连 DB、残留 Mock 假数据、`.logs` 运行时报错、缺失关键错误处理。
   - **`[P2]` 架构与规范偏差**：缺少 Google Style 导出注释、四态不完整、组件放错目录、冗余抽象/死代码。
   - **`[P3]` 轻微改进建议**：局部可读性、命名微调（不阻塞进入下一 Phase）。
   - 每条问题必须标明：`[级别] 分类（缺陷 / 规范）`、`文件:行号`、`违反的基准或规则`、`具体问题与影响`、`最小修复建议`。同一根因问题合并为一条。
3. **基准对齐与检查实录**：
   - `demo/` 与 `docs/plan.md` 本 Phase 覆盖情况；
   - 实际运行的命令与退出码、`.logs/*.log` 检查结果；
   - **未验证事项**（例如未启动浏览器视觉走查、未执行 E2E 等，必须诚实列明）。
